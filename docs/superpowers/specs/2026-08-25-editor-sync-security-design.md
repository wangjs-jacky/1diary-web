# 一本日记编辑器、同步与安全修复设计

日期：2026-08-25

## 目标与范围

本次升级在不改变“一本日记”单栏时间流和莫兰迪视觉方向的前提下，一次性解决四类问题：编辑器难用、图片无法调整尺寸、日期/时间/分类控件过于原生，以及附件失败导致所有日记长期停留在“等待同步”。同时收紧 Supabase 公共表的直接访问权限，并将修复部署到现有 ECS。

不在本次范围：天气、会员、数据导入迁移、多人协作、PWA 安装能力、端到端加密。

## 已确认现状与根因

- 编辑页使用原生 `contentEditable` 和 `document.execCommand`，格式状态不可见，取消格式缺少明确入口，HTML 与 Markdown 转换容易丢失语义。
- 日期、时间和分类直接使用浏览器原生输入控件，不同平台表现不一致，也不符合既有视觉体系。
- 图片只保存附件引用，没有显示宽度元数据，因此编辑页和时间流都只能按原始/容器宽度展示。
- 同步流程在推送 outbox 前先上传全部待处理附件；任何一个附件上传失败都会抛错并终止本轮推送，导致不相关的文本日记也无法同步。
- OSS bucket 当前没有 CORS 配置，浏览器无法完成后端签发的直传请求。服务器日志因此只出现反复 `prepare`，没有 `complete` 和后续 `sync/push`。
- Supabase `public` schema 的业务表未启用 RLS，且暴露给客户端角色；当前产品架构实际只需要客户端使用 Supabase Auth，业务数据全部经过自有 API。

## 编辑器设计

使用 Tiptap 替换原生编辑器，文档的持久化格式继续采用 Markdown，避免修改现有后端字段和同步协议。

工具栏固定显示在正文上方，提供：正文、二级标题、加粗、斜体、无序列表、有序列表、引用、行内代码、撤销、重做和清除格式。按钮反映当前光标/选区的激活状态；再次点击激活按钮即可取消该格式。“正文”将当前块恢复为普通段落，“清除格式”同时移除行内标记和块级格式。保留常用 Markdown 输入快捷方式。

编辑器直接从 Markdown 初始化，并在内容变化时输出 Markdown。对历史内容保持兼容；解析失败时不丢弃原文，而是保留为可编辑文本。标题、正文、分类、标签、发生时间和字数统计继续沿用现有数据结构。

## 图片设计

继续支持剪贴板粘贴和文件选择。附件在编辑器中表现为可选择的图片节点：点击后显示边框和缩放控制，支持拖拽等比缩放，并提供 25%、50%、75%、100% 四个快捷宽度。宽度限制在 20% 至 100%，默认 100%。

Markdown 使用向后兼容的扩展语法保存显示宽度：

```markdown
![说明](attachment://附件ID){width=50%}
```

没有宽度后缀的历史图片按 100% 展示。编辑器、时间流预览和再次编辑必须对该语法往返一致。图片上传状态与日记同步状态分开呈现，上传失败时显示可重试提示，但不清空正文或删除本地图片。

## 表单控件设计

日期、时间、分类、标签和提示浮层采用 React Aria Components，并使用现有 CSS 变量实现莫兰迪风格，不引入 Tailwind。日期选择器使用可键盘操作的日历弹层，时间使用 TimeField，分类使用 Select。所有控件具备清晰的焦点、选中、禁用和错误状态。

React Bits 不承担编辑器、日历或选择器等基础交互；它更适合装饰性动效。本次优先使用具备无障碍语义和完整交互状态的组件库，避免再次封装原生控件。

## 同步与恢复设计

同步分为两条可独立推进的队列：附件传输和业务 outbox。附件失败只阻塞直接依赖该附件的草稿/发布操作，不阻塞其他日记、分类、标签或删除操作。每轮同步执行以下步骤：

1. 注册设备并拉取服务端变化。
2. 尝试上传待处理附件，记录成功和失败的附件/草稿集合，不因单个失败终止整轮。
3. 将 outbox 分为“本轮可推送”和“依赖失败附件需延期”两组。
4. 推送可执行操作并应用服务端结果；延期操作保留在本地队列。
5. 汇总同步状态：已同步、等待同步、同步中、部分失败或离线，并给出可重试动作。

OSS bucket 增加最小化 CORS：仅允许当前 Web 来源 `http://121.43.32.242:3080`，允许上传/读取所需的 `POST`、`GET`、`HEAD`，允许请求头，暴露 `ETag`。部署后用真实浏览器直传验证 `prepare -> OSS -> complete -> sync/push` 完整链路。将来切换域名/HTTPS 时同步替换允许来源。

现有本地待同步日记不重建、不清库。CORS 修复后由队列自动重试并恢复；验证成功前保留 IndexedDB 数据。

## Supabase 访问控制

客户端继续只直接调用 Supabase Auth。对全部业务表撤销 `anon` 与 `authenticated` 的直接表权限并启用 RLS，不创建客户端数据访问策略，形成默认拒绝。部署前确认后端数据库连接角色为表所有者或服务端专用角色，迁移不会阻断 API；迁移后运行 Supabase 安全顾问，确认公开表告警消除，并以真实 API 冒烟测试验证后端读写。

该迁移不改变表结构、数据或同步协议，可通过对应回滚迁移恢复授权与 RLS 状态，但正常回滚优先回退应用并保留更严格的数据库权限。

## 测试与验收

- 单元测试：Markdown 格式开关、清除格式、附件宽度解析/序列化、历史图片兼容、附件失败时 outbox 分流、失败后恢复重试。
- 静态检查：前端 lint/typecheck/test/build，后端 lint/typecheck/test/migration 检查。
- 浏览器回归：登录、新建纯文本日记、格式添加和取消、粘贴图片、拖拽与预设缩放、修改日期/分类、自动保存、离线编辑后恢复同步、刷新后内容与图片宽度保持。
- 服务验证：OSS CORS 精确来源生效；后端健康检查正常；同步日志出现附件 complete 与 sync push；Supabase 顾问无公共表 RLS 告警。

## 发布与回滚

先提交并推送前后端代码，再配置 OSS CORS 和执行数据库迁移，随后滚动更新后端与前端容器。每一步完成后执行健康检查；最终在生产地址进行浏览器回归。

前端或后端失败时回滚到上一镜像/提交。OSS CORS 可恢复原配置；数据库权限迁移保留独立回滚脚本。任何回滚都不删除用户 IndexedDB、Supabase 业务数据或 OSS 对象。
